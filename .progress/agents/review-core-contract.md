## Находки

### 1. [medium] hooks/computeVisible.ts:39 — в searchItems передаётся отфильтрованное подмножество, кэш индекса перестраивается при каждой смене раздела/фильтра
`computeVisible` сначала фильтрует записи (base + uiFilter) и отдаёт в `searchItems(pre, ...)` только `pre`.
`syncIndex` приводит модульный кэш ровно к переданному набору: всё, чего нет в `pre`, — discard, новое — add.
Сценарий: 3000 записей, запрос «react» во Входящих (40 записей) → в индексе 40 документов; переход в Базу знаний
(2500) → 40 discard + 2500 add по одному; обратно — 2500 discard (или полный rebuild). `prepareSearchIndex(allItems)`
в idle бесполезен: первый же поиск из раздела выбросит большую часть индекса. Два потребителя с разными наборами
(список + палитра команд по всей базе) будут перестраивать индекс на каждом рендере.
Исправление: в `searchItems` передавать все записи, а base/uiFilter применять после (или дать searchItems
параметр-предикат/extra filter); индекс всегда синхронизировать с полным набором.

### 2. [medium] search/filter.ts:29,31 vs db/repo.ts matchesFilter — две публичные функции с одним именем и разным поведением
- `favorite: false`: repo — «не фильтровать» (галочка), search — «только НЕ избранные».
  `matchesFilter(favItem, { favorite: false })` → repo: true, search: false.
- `tags`: repo нормализует теги фильтра и пропускает пустые, search сравнивает строго.
  `{ tags: ['React'] }` или `{ tags: ['#react'] }` для записи с тегом `react` → repo: true, search: false;
  `{ tags: [''] }` → repo: true, search: false.
Обе экспортируются (`@/db/repo` и `@/search`), контракт объявляет только repo-версию. UI-агент, взявший
`matchesFilter` из `@/search`, получит другой результат на тех же данных. Сейчас через `searchItems` расхождение
не проявляется (parseQuery даёт только `favorite: true` и нормализованные теги), но это случайность.
Исправление: оставить одну реализацию (search/filter.ts — чистая, repo реэкспортирует) либо убрать экспорт из
`@/search` и выровнять семантику favorite/tags.

### 3. [low] db/repo.ts:214–249 (deleteItems) — пакетное удаление связанных записей портит снимок для «Отменить»
При удалении [A, B], где A↔B связаны: на шаге A записи B делается `update({links, updatedAt: now})`, затем B
читается уже изменённой и попадает в снимок с `updatedAt = момент удаления`. После `restoreItems` у B
updatedAt ≠ исходному (нарушено «отмена — как будто ничего не было»): сортировка «по изменению» поднимает B наверх.
Связь восстанавливается корректно. Исправление: сначала прочитать все удаляемые записи (bulkGet) и строить снимки
из исходных, обратные ссылки чистить только у записей вне списка удаления.

### 4. [low] db/repo.ts:537 (sortTitle) vs lib/itemTitle.ts displayTitle — разные правила производного заголовка
sortTitle: `title || linkMeta.title || fileName || content` (весь content, без url). displayTitle: … первая строка
content → url. Ссылка без заголовка/метаданных/комментария (demo-08) показывается как
«https://developer.mozilla.org/…», но при сортировке «по названию» считается «без заголовка» и уходит в конец
списка, а не к букве «h». Исправление: в repo использовать displayTitle (или добавить fallback на url).

### 5. [low] db/repo.ts:482 (updateCategory) — переименование допускает дубль имени, который импорт и поиск потом склеивают
`createCategory` дедуплицирует по имени, `updateCategory` — нет. Сценарий: «Работа» (A) и «Проекты» (B),
B переименовать в «работа» → `cat:работа` находит только записи A (resolveCategoryName берёт первую);
экспорт → импорт (`replace`): B отбрасывается как дубль по имени, её записи молча переезжают в A.
Исправление: в updateCategory отклонять/сливать имя, совпадающее (без регистра) с другой категорией.

### 6. [low] db/seed.ts:189 — у архивных демо-записей с prevStatus 'library' нет processedAt
`processedAt` ставится только при `status === 'library'`; demo-27/29/30 (архив, prevStatus: 'library') — без него,
хотя по инварианту setStatus запись, побывавшая в library, имеет processedAt. При «Вернуть из архива»
`unarchive` выставит processedAt = now: запись 50-дневной давности показывается как обработанная только что.
Исправление: `isLib = status === 'library' || prevStatus === 'library'`.

### 7. [low] search/query.ts:139 + filter.ts:29 — фильтр по тегу не следует заявленному «ё = е»
Свободный текст сворачивается через fold (NFKC, ё→е), а `#тег`/`tag:` сравнивается с `item.tags` строго.
Запись с тегом `ёлка`: запрос «елка» находит её (поле tags в индексе), а `#елка` — нет. Аналогично тег `отчёты`
из демоданных: `#отчеты` → пусто. Исправление: сравнивать `fold(tag)` с обеих сторон в фильтре поиска.
